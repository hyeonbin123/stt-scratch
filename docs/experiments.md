# 측정 규칙과 결과

규칙은 재기 전에 적고 커밋한다. 결과는 각 단계 절의 "결과" 소절에만 적고, 규칙을 바꾸면 "규칙 변경" 절에 이유와 시점을 남긴다. 봉인 test는 7단계에서만, 사전 등록한 구성으로 각 1회 잰다.

## 공통 (2026-10-11 규칙, 측정 전)

### 지표
- **주지표 CER_ns**: 공백 제외 음절 CER. 정규화는 whisper-ko-ft와 같다: 소문자화, 글자·숫자·공백·작은따옴표가 아닌 문자는 공백으로, 한국어는 작은따옴표와 공백을 모두 없앤 뒤 글자 단위 편집 거리. 묶음 전체의 편집 수 합 ÷ 정답 글자 수 합. whisper-ko-ft의 Zeroth test 앵커(turbo 제로샷 4.48 %, turbo+LoRA 1.96 %)가 이 정의다
- **보조 CER_ws**: 공백 포함 음절 CER(공백도 글자로 셈, KsponSpeech 정의)
- 구간: 발화 단위 부트스트랩 1,000회, seed 0, 95 %. 두 구성의 비교는 같은 발화를 다시 뽑는 짝지은 구간
- 모든 수치에 체크포인트(epoch, 평균 개수)와 디코딩 모드(full / simulated chunk / real streaming)와 청크·좌측 문맥을 함께 적는다
- 정답에 아라비아 숫자·라틴 문자가 남는 발화(FLEURS·CV)는 **전체**와 **한글 전용 부분집합** 두 수치를 모두 보고한다. 모델 어휘에 숫자·라틴이 없으므로 전체 수치에서는 그 글자가 오류로 센다

### 텍스트 정규화 (학습 정답·평가 정답 공통, 스크립트 하나)
1. NFC 정규화
2. 한글·라틴 문자·숫자·공백 외 문자(문장부호·기호)는 공백으로
3. 공백 축약, 양끝 제거
4. 숫자가 든 발화는 **학습에서 제외**(한국어 숫자 읽기가 둘이라 자동 변환이 틀리기 쉬움). 평가에서는 위 "두 수치" 규칙
5. 라틴 문자만 든 발화도 학습에서 제외(어휘는 한글 음절만). 제외 수는 세트별로 보고

### 어휘
- blank(0), `<unk>`(1), 공백(2), 그다음 학습 전사(정규화·제외 뒤)에 1회 이상 등장한 한글 음절 전부(빈도순). 평가 세트별 OOV 음절 수를 CER 하한으로 보고

### 데이터 분할 (SHA-256, seed 없음)
- Zeroth 고유 문장 3,003개를 `sha256("zeroth-holdout:" + 문장)`의 앞 8자리 16진수를 정수로 보아 `% 100`이 `< 10`이면 **홀드아웃 H**(약 300문장, 그 문장의 발화 전부 ≈ 2,200발화 ≈ 5 h). H 안에서 `% 100`이 `< 5`면 **dev_H**, 아니면 **test_H**(봉인)
- 학습 = Zeroth train − H + FLEURS train(제외 규칙 뒤) + CV22 validated − CV22 dev − CV22 test(path 기준)
- **dev_mix**(1차 선택 지표) = FLEURS validation(한글 전용) + CV22 dev(한글 전용). 두 세트의 편집 수·글자 수를 합쳐 하나의 CER로 계산
- **dev_H**(2차 가드) = Zeroth 홀드아웃 dev
- **봉인 test**(7단계 1회) = Zeroth 공식 test 457(본 문장·못 본 화자, 표시 붙임), Zeroth test_H(못 본 문장·본 화자), FLEURS test 382, CV22 test 472
- Common Voice `other`(미검증)와 `invalidated`는 쓰지 않는다
- 길이 20 s 초과 발화는 학습에서 제외. 25 fps 출력에서 `T' < U + (연속 같은 토큰 수) + 1`인 발화도 제외(CTC 손실 무한대 방지). 모두 수를 보고

### 선택 규칙 (모든 단계 공통)
- 후보 사이 비교는 dev_mix의 CER_ns로 하고, dev_H가 절대 0.3 넘게 나빠지는 후보는 채택하지 않는다
- 채택 임계는 **max(0.3 절대, 2s)**. s = 1단계에서 같은 설정 3시드의 dev_mix CER_ns 표준편차. 상대 기준을 쓰는 가설은 짝지은 부트스트랩 구간이 0을 제외해야 한다
- 같은 비교 안의 런은 같은 업데이트 step 수·배치 규칙·시드를 쓴다(메모리가 남아도 배치를 키우지 않음)
- 체크포인트는 매 epoch 저장, 평가 모델은 dev_mix 상위 10개 평균

### 예산 규칙
- 0단계에서 잰 epoch 시간 × 100 > 14 h이면 2단계 epoch = floor(14 h ÷ epoch 시간), 하한 60. 적용하면 기록
- 단계마다 GPU 시간을 기록한다. 다른 프로그램이 GPU를 쓰는 동안 잰 속도·지연은 "부하 조건"으로 표시한다

### fp16 규칙
- `torch.autocast(device_type="cuda", dtype=torch.float16)` 명시, 파라미터·옵티마이저 fp32, GradScaler 기본값, `unscale_` 뒤 grad clip 5.0
- CTC와 자기조건 CTC 입력은 `log_softmax(..., dtype=float32)`. 단위 테스트로 고정
- **fp16 발산 판정**: 손실 NaN/Inf 3회 이상, 또는 GradScaler scale < 1.0이 100 step 연속, 또는 3 epoch까지 dev CTC 손실이 내려가지 않음. 발산한 런은 기록하고 LR×0.5로 최대 2회 재시작. 발산 횟수는 최종 보고에 표로 남긴다
- 시작 로그에 `torch.cuda.is_bf16_supported(including_emulation=False)` 값을 남긴다(2080 Ti는 False여야 함)

## 0단계: 데이터·코드·마이크로벤치 (2026-10-11 규칙, 측정 전)

### 할 것
- 정규화 스크립트·어휘·분할 매니페스트를 만들고 `manifests/`에 커밋
- 모델·학습·디코딩 코드와 단위 테스트
  - 미래 누출: 미래 프레임을 난수로 바꿔도 현재 청크까지의 출력이 불변(청크 4/8/16/32, 좌측 64/128)
  - 스트리밍 == 오프라인: 캐시 스트리밍 forward와 전체 발화 + 청크 마스크 forward의 log-prob 최대 차이 fp32 1e-5, fp16 1e-2 이내(fbank 경계 프레임 포함)
  - CTC 입력 dtype == float32
  - 과적합: 발화 20개로 CER 0 수렴
- 마이크로벤치: max-duration {200, 300, 400, 600} s에서 피크 메모리·step 시간·데이터 대기 비율, epoch 시간 추정, SDPA 커널 종류

### 가설
- **H0.1**: 25 fps에서 CTC 길이 제약에 걸리는 학습 발화 ≤ 0.5 %
- **H0.2**: max-duration 300 s 피크 메모리 ≤ 9.5 GB, 학습셋 1 epoch ≤ 8분

### 판정
- 단위 테스트 전부 통과 전에는 학습을 시작하지 않는다
- H0.1 위반 발화는 제외하고 비율을 기록. H0.2 위반이면 예산 규칙 적용
- 데이터 대기 비율 > 20 %면 fbank fp16 사전 계산으로 전환하고 기록

### 0단계 결과 보강 (2026-10-11, 1단계 측정 전)
- **1단계 첫 시도 무효**: LR 1e-3 시드 1·2·3이 모두 100~120 step에서 scale < 1.0 100 step 연속으로 멈췄다. 원인은 fp16 불안정이 아니라 CTC 손실 코드의 버그 둘(패딩 프레임의 초기화되지 않은 CTC 기울기, 전치된 비연속 log-prob 뷰에서 CUDA CTC backward 오류; `docs/ai-verification.md`). 수정 뒤 실패 배치 16시드에서 NaN 0회. 세 런은 발산 횟수 표에 "코드 버그로 무효"로만 적고 H1에 넣지 않는다(`reports/stage1/attempt1-invalid-summary.json`)
- **독립 검토 반영**: Codex 0단계 검토 16건을 모두 반영했다(규칙 변경 1~10, `docs/ai-verification.md`). 테스트는 56개(`test_model` 38, `test_prepare_data` 13, `test_service` 5)
- **fp16 게이트 실측**(RTX 2080 Ti, 실제 크기 12층 d=256 1,288 클래스, 무작위 초기화, 800 mel 프레임): 캐시 스트리밍 vs 오프라인 청크 마스크 log-prob 최대 절대차 fp16 autocast 3.4e-3~4.0e-3(청크 4/64, 8/128, 16/128; 캐시 절단 포함), fp32 ≤ 2.9e-6 → 등록 게이트(fp16 1e-2, fp32 1e-5) 충족. fp16에서 청크 경계 뒤 음성을 바꿔도 경계 앞 출력은 비트 단위로 같다(BACON 우측 탭을 가린 뒤 더하는 구현)
- 학습 루프 연기 실행(12 step): 시작 scale 65,536이 256까지 내려오는 동안 8 step 스킵, 이후 업데이트. 이 초기 스킵은 GradScaler의 정상 동작이라 발산 규칙(scale < 1.0)과 무관하다

## 1단계: fp16 안정성·peak LR (2026-10-11 규칙, 측정 전)

- 후보: peak LR {1e-3, 2e-3} × 시드 {1, 2, 3}, warmup 2,000 step(규칙 변경 1; 원래 4,000), 최종 구성 그대로 5 epoch
- 측정: 런별 발산 여부(위 정의), epoch 5의 dev_mix·dev_H CER_ns(full greedy), GradScaler 스킵 횟수와 scale 이력
- **H1**: 2e-3에서 발산 ≤ 1/3
- 판정: 발산 0/3인 LR 가운데 epoch 5 dev_mix 평균이 낮은 쪽을 채택. 둘 다 발산이 있으면 5e-4·warmup 8,000을 더해 반복. 채택 LR의 3시드 표준편차를 s로 기록

### 1단계 결과 — 2차 시도 (2026-10-11 03:22~05:14, `reports/stage1/attempt2-*`)
- 6런 모두 발산 판정. 5런은 규칙 변경 3의 dev 손실 조건(epoch 3 ≥ epoch 1)으로 epoch 3에서 멈췄고(dev_mix 손실 예: 187.3 → 189.7 → 192.2), 1런(2e-3 시드 3)은 warmup이 끝난 직후 step 2,100 부근에서 기울기 노름 67,244·scale 0.5로 scale < 1.0 100 step 조건에 걸렸다(진짜 fp16 불안정)
- 멈춘 시점의 모델은 모두 CTC 학습 초기의 "사전확률 해"에 있었다: dev_mix full CER 0.93~0.95, 출력은 "이 … 니다"뿐, blank 사후확률 평균 0.69. 학습 손실도 step 300 이후 140~390 사이에서 흔들리며 내려가지 않았다

- 부수 측정: epoch 시간 261~274 s(첫 epoch는 디스크 캐시 때문에 470~572 s), 0단계 추정 7.8분보다 짧다. 초기 GradScaler 스킵 9~18회(scale 65,536 → 64~128 안착)

### 1단계 진단 (2026-10-11 05:17~06:05, 판정에 쓰지 않는 탐색 실험, `work/diag/`)
- **이어 학습**: 1e-3 시드 1의 epoch 3 체크포인트에서 LR 1e-3(warmup 200, 6 epoch cosine)으로 5 epoch 더 → dev_mix CER 0.935 그대로, dev 손실 183.9, 기울기 노름 1,479 → 4,564 → 37,436으로 커지다 step 3,600에서 scale 붕괴. 정체가 아니라 불안정

### P3: step 연산 수 줄이기와 CUDA Graph (H6.2 후속)
- 후보 경로(`StreamingEncoder(path=...)`, 서버 `--step-path`): **fast** = step마다 RoPE 표·청크 마스크를 한 번만 만들어 모든 블록에 넘김, 입력이 청크 하나 안일 때 BACON 오른쪽 탭 가리기(0을 0으로 바꾸는 일) 생략, CUDA fp16 autocast 아래에서는 Linear·conv 가중치를 미리 fp16으로 바꾼 복사본(LayerNorm·정규화 버퍼는 fp32)을 씀. **graph** = fast + 캐시가 꽉 찬 정상 상태 step(17번째 청크부터)을 고정 버퍼 위에서 수동 `torch.cuda.CUDAGraph`로 캡처해 재생(첫 16청크와 flush의 부분 청크는 fast). 둘 다 eager와 같은 값을 같은 순서로 계산하도록 고른 변경이다(CPU fp32·bf16 autocast에서 비트 단위로 같음: `tests/test_fast_streaming.py`)
- **출력 동일성 관문 G3**(gate): 경로마다 (가) dev_H 앞 30발화의 청크별 fp32 log-prob이 eager와 최대 절대차 ≤ 1e-3(GPU fp16; 설계상 기대값 0)이고 CPU fp32 앞 5발화도 ≤ 1e-3, (나) dev_H 전수(1,113발화) 실제 캐시 스트리밍 greedy 전사가 eager와 모두 같음. graph를 먼저 재고, graph가 통과하면 fast는 (가)만 본다(graph의 정상 상태가 아닌 step이 fast 코드다). graph가 통과하지 못하면 fast도 (나)를 잰다. 그래프 캡처가 실패하면 graph는 고정 버퍼 코드를 그래프 없이 돌고 그 사유를 결과에 남긴다
- 지연(timing): 6단계 격자와 같은 정의(dev_H 앞 30발화 GPU fp16, 앞 10발화 CPU fp32 1스레드, step 전후 동기화, 마지막 부분 청크 포함)로 GPU {eager, fast, graph} × {12층, 6층}, CPU {eager, fast} × {12층, 6층}를 같은 실행에서 잰다(eager도 다시 잰다). 경로마다 무작위 mel 24청크와 첫 발화로 예열한 뒤 잰다(가중치 복사·그래프 캡처의 1회성 비용 제외; 서버도 시작 때 예열한다). 모든 청크 p50/p90/max·RTF와 정상 상태 청크 p50/p90을 보고
- **판정**: 관문을 통과한 경로 가운데 같은 실행의 eager보다 모든 청크 p90이 낮은 것 중 가장 빠른 것을 서버 기본 step 경로로 한다(GPU 후보 graph·fast, CPU 후보 fast). 없으면 eager 유지. H6.2는 6단계 판정(미충족)을 바꾸지 않고 "후속 구현에서 p90 x ms"로 덧붙인다

### P1: 끝점 뒤 전체 문맥 2차 패스 (제품 선택: 확정 자막이 부분 자막을 대체)
- 정의(`StreamSession(final_pass="full")`, 서버 `--final-pass full`): 세그먼트가 닫힐 때(rule1·2·3, flush) 그 세그먼트에서 인코더에 넣은 mel 전체(끝점을 낸 청크·flush의 부분 청크 포함, 이전 세그먼트 문맥 없음)를 같은 모델의 전체 문맥 모드 `ChunkSpec(0, -1)`로 greedy 디코딩해 확정 자막으로 쓴다. 길이는 128 mel 프레임 배수로 0을 덧붙이고 실제 길이를 넘긴다(유효 프레임 출력 불변: `tests/test_final_pass.py`). 서버는 시작할 때 길이 묶음마다 한 번씩 예열한다. 부분 자막과 끝점 판정은 지금과 같다
- 비교: 같은 세션 실행에서 1-pass 확정(지금 서비스: 320 ms 스트리밍 텍스트) vs 2-pass 확정. 세션 조건은 6단계와 같다(발화마다 뒤에 −60 dBFS 잡음 3 s, 끝점 뒤 캐시 유지). dev_mix는 rule2 1.2 s·0.8 s 두 실행, dev_H는 P2에서 고른 rule2 한 실행
- 지표: 세션 CER_ns(한글 전용)와 짝지은 95 % 구간(2-pass − 1-pass), 2차 패스 계산 시간 p50/p90(GPU fp16, 앞뒤 동기화, greedy 포함 = 끝점 판정 뒤 확정 자막이 늦어지는 시간), EP50/EP90(6단계 정의)과 "EP + 첫 끝점의 2차 패스 시간", 확정 때 텍스트가 바뀐 세그먼트 비율(공백 포함·제외), UPWR/UPSR(1-pass 확정 기준은 6단계와 같고, 2-pass 확정 기준은 부분 자막이 확정 때 고쳐지는 정도), CPU fp32 1스레드 2차 패스 p50/p90(final-cpu: dev_mix 앞 50발화 세션)

- 측정 도구 보완(측정 전, 기록 수치 무관): 서버는 2차 패스를 켜면 final·endpoint 이벤트에 `stream_text`(같은 세그먼트의 2차 패스 전 320 ms 스트리밍 텍스트)를 더 보낸다(추가 필드라 페이지·기존 클라이언트에 영향 없음). `scripts/stream_client.py`는 발화마다 닫힘 이벤트(stream_text·final_pass_ms·endpoint 포함)를 기록하고, 요약은 기록의 서버 설정(`-meta.json`의 `server_info.final_pass`)에 따라 비교를 고른다: none(또는 그 키가 없는 2차 패스 이전 서버)이면 6단계처럼 확정 텍스트를 simulated 가설과, full이면 stream_text 이음(비지 않은 값을 공백으로 이음)을 simulated 가설과 비교하고 확정 텍스트는 `--replay-check`(같은 `/info` 설정의 오프라인 StreamSession에 같은 패킷을 서버 처리기와 같은 순서로 재생한 기대 결과)와 비교한다. 판별할 수 없으면 null과 경고를 남긴다. 커밋된 6단계 클라이언트 기록을 새 요약으로 다시 계산하면 기록된 값이 그대로 나온다(`tests/test_stream_client.py`). `scripts/stage6.py drift`에 `--step-path`·`--final-pass`·`--warm-up`(기본값은 6단계 동작 그대로), `scripts/followup.py`에 `continuous` 하위 명령을 더했다

## 확정 자막 어절 신뢰도 (2026-10-29 규칙, 측정 전)

끝점 뒤 2차 패스(규칙 변경 26 P1, 서버 기본값)가 내는 확정 자막의 어절마다 '틀렸을 가능성'을 알려 주는 신뢰도를 dev에서 재는 측정이다(규칙 변경 28). 이유: 처음 보는 문장에서 CER이 15~16 %(봉인 test_H 15.55 %)인 모델이라 의심할 어절을 알려 주는 신호가 실용적인데, 2차 패스는 전체 문맥 log-prob을 계산한 뒤 greedy id만 남기고 버린다. CTC 사후확률은 한 프레임에 몰리는 뾰족한 분포라 과신하기 쉽고 학습 문장을 암기한 Zeroth 영역은 더할 수 있어 그대로 확률로 읽을 수 없으므로 보정까지 등록한다. 후보는 프레임 엔트로피를 정규화해 토큰·어절로 모으는 학습 없는 신뢰도가 프레임 최대 확률보다 오류 어절을 잘 가른다는 보고(Laptev·Ginsburg, SLT 2022, arXiv:2212.08703)를 따라 두 계열을 둔다. 새 지표라 기록 수치·판정과 서버 기본값은 바꾸지 않고, 봉인 test는 열지 않는다(dev_mix·dev_H만).

- 덤프(`scripts/final_pass_dump.py`, GPU): 최종 모델(SHA-256 6502406c…)로 P1 세션 조건(발화마다 새 세션, 발화 뒤 −60 dBFS 잡음 3 s·seed = 발화 인덱스, 서버 명령행 기본 구성 = 320 ms 청크·좌측 128·rule2 0.8 s·끝점 뒤 캐시 유지·GPU graph·2차 패스 full·fp16 autocast)으로 dev_mix 700·dev_H 1,113발화를 흘리고, 세그먼트마다 2차 패스 로짓에서 프레임별 argmax·최대 log-prob·엔트로피(전체 어휘 분포에서 계산)·blank log-prob·top-10 (id, log-prob)을 `outputs/followup/final_pass_dump/`에 저장한다(커밋 안 함; 체크포인트 SHA-256·코드 커밋·어휘 SHA-256과 세그먼트별 확정 텍스트·stream_text를 함께 남긴다). 서비스 코드는 바꾸지 않는다(세션을 상속해 2차 패스 forward 출력만 받는다). 정확도 측정이라 쉬는 상태는 기다리지 않는다
- **재현 조건**: 덤프의 발화별 확정 가설(final 텍스트 이음)이 P1 확정 가설(`reports/followup/hyps/{dev_mix,dev_h}-session-rule2_0.8-final_pass.jsonl`)을 재현해야 한다. 한글 전용 CER_ns가 P1 값(dev_mix 22.847 %, dev_H 16.015 %)과 각각 0.02포인트 안(P1 (d)와 같은 허용 폭)이고, 정확히 같은 발화 수도 보고한다. 어긋나면 판정하지 않고 원인을 찾는다
- 어절과 점수(`src/stt_scratch/confidence.py`): 가설 어절 = 확정 텍스트를 공백으로 나눈 것(`<unk>`는 U+318D 한 글자로 어절에 남는다). 토큰 구간 = greedy가 토큰을 낸 프레임부터 같은 argmax가 이어지는 프레임까지. 토큰 점수 두 가지: entropy = 1 − (구간 최소 엔트로피) / log V(V = 1,288), maxprob = 구간 최대 사후확률. 어절 점수 = 그 어절 음절 토큰 점수의 최솟값 또는 평균(공백 토큰 제외). 후보 4개(이 순서가 동점 순서): entropy_min, entropy_mean, maxprob_min, maxprob_mean
- **정오 라벨**: 정답(학습 정규화)과 가설 어절을 편집 거리(대치·삽입·삭제 각 1)가 가장 작은 정렬 가운데 일치가 가장 많은 정렬로 맞추고(그래도 같으면 끝에서부터 대치·일치 > 삭제 > 삽입), 일치 = 정답 어절, 대치·삽입 = 오류 어절로 한다. 삭제(빠진 정답 어절)는 붙일 가설 어절이 없어 신뢰도 대상이 아니고 수만 보고한다. 편집 수는 jiwer와 같지만, jiwer의 정렬은 편집 수가 같은 정렬 사이에서 일치가 적은 쪽을 고를 수 있어(예: 정답 '할 수 있다 가나', 가설 '할수 있다 다라 마'에서 맞게 나온 '있다'까지 대치) 라벨에는 쓰지 않는다. 띄어쓰기만 다른 오류(일치 사이 구간에서 정답·가설 어절을 공백 없이 이으면 같은 것)도 오류로 센다
- 대상과 절반: 한글 전용 발화(주지표와 같은 부분집합; dev_mix 633, dev_H 1,113). dev_mix 한글 전용 발화를 id(UTF-8) SHA-256 첫 바이트가 짝수면 절반 A(297발화), 홀수면 절반 B(336발화)로 나눈다(seed 없음, 결과를 보기 전에 센 수)
- 선택(절반 A만, `scripts/confidence_eval.py`): 후보마다 AUROC를 재 가장 높은 후보를 고르고, 그 후보로 Platt 보정 p = σ(a·logit(s) + b)를 맞춘다(s는 [10⁻⁶, 1 − 10⁻⁶]로 자름; Platt(1999)의 목표값 평활과 Lin·Lin·Weng(2007)의 뉴턴법)
- **판정(절반 B 한 번)**: 보정 확률로 잰 오류 어절 검출 AUROC(무작위 (정답, 오류) 어절 쌍에서 정답 어절의 확률이 더 높을 확률, 같으면 1/2) ≥ 0.80이고 ECE(같은 폭 15구간) ≤ 0.05이면 **채택** = final 이벤트의 선택 필드 `words: [{w, conf}]`와 화면 밑줄 옵션을 측정 뒤 별도 커밋으로 제공한다(서버 기본값은 그대로, 기본 화면 표시는 사용자 결정). 아니면 보고만 한다. 판정은 점추정으로 하고 발화 부트스트랩 95 % 구간(seed 0, 1,000회, 어절이 아니라 발화를 뽑음)을 함께 적어, AUROC 구간 하한이 0.80 미만이거나 ECE 구간 상한이 0.05를 넘으면 "점추정으로만 충족"이라고 적는다
- 보고(판정 없음): 절반 B의 후보별 AUROC(선택은 A에서 했음을 함께 적음), 보정 전 ECE, Brier 점수, 밑줄 임계 τ = 보정 확률 0.5에서 밑줄 비율·정밀도(밑줄 어절 가운데 오류)·재현율(오류 가운데 밑줄), 띄어쓰기만 다른 오류 수와 그것을 정답으로 본 AUROC·ECE, 숫자·라틴을 포함한 절반 B의 AUROC·ECE, dev_H(같은 선택·보정 그대로)의 같은 지표와 구간(Zeroth 영역 과신 확인용 참고치), 어절 정렬 수와 WER
- 명령·결과·시간: `uv run --no-sync python scripts/final_pass_dump.py --manifests dev_mix,dev_h`(GPU 약 35분: P1의 같은 두 세션 실행이 부하 조건에서 725 s·1,170 s였다) → `uv run --no-sync python scripts/confidence_eval.py`(CPU 수 분) → `reports/followup/confidence.json`. 덤프에는 top-10과 blank log-prob을 함께 남겨 다른 확정 자막 디코딩 평가가 GPU 없이 다시 쓸 수 있게 한다
- 해석 주의(측정 전 예상): dev_H(Zeroth 영역)는 학습 문장 암기로 같은 보정에서도 과신(ECE 증가)이 클 수 있다. 라벨이 어절 단위라 띄어쓰기 오류가 많으면 AUROC가 낮아질 수 있다(띄어쓰기 민감도 보고로 확인)

## 규칙 변경

1~16은 2026-10-11이다. 1~11과 14는 1단계 2차 시도 전(커밋 d095b8e·3cece48, 03:21), 13은 2차 결과와 진단을 본 뒤 3차 시도 전(커밋 b6e27a0 07:02, 3차 시작 07:23), 15~16은 1단계 판정 뒤 2단계 측정 전(Codex 1단계 검토 반영). **12번은 비어 있다**: 처음 등록 때 12번이던 '서비스 경로 정밀도·버퍼'가 커밋 b6e27a0에서 13번을 넣으며 14번으로 바뀌었다(내용·등록 시점은 그대로; 2026-10-15 문서 정정). 17번부터는 항목마다 날짜를 적었다. 26번은 7단계 봉인 test 뒤의 후속 등록이다. 1단계 첫 시도는 코드 버그로 무효 처리(0단계 결과 보강 참조). 독립 검토(Codex, `docs/ai-verification.md`)의 지적을 반영했다.

1. **warmup 4,000 → 2,000 step(모든 단계)**. 1단계 5 epoch = 3,485 step이라 warmup 4,000 안에서 끝나 peak LR에 닿지 않는다(마지막 LR이 peak의 87 %). 2,000 step ≈ 2.9 epoch. 2단계(69,700 step)도 2,000
2. **step 정의**: "같은 업데이트 step 수"를 "같은 optimizer step 시도 횟수"로 읽는다. LR 스케줄·예산·동일 비교는 시도 횟수 기준이고, GradScaler가 건너뛴 횟수(`skipped`)와 실제 업데이트 수(`updates`)를 모든 런에서 함께 기록·보고한다
3. **dev CTC 손실 발산 조건 구체화**: 매 epoch 끝에 dev_mix의 최종 헤드 CTC 손실(full context, 발화 평균, 학습과 같은 정밀도)을 기록하고, **epoch 3 끝 값 ≥ epoch 1 끝 값**이면 발산으로 판정해 런을 멈춘다. 처음부터 학습하는 런에만 적용(`--init`로 이어 학습하는 4단계에는 적용하지 않음)
4. **라틴 제외 문구**: "라틴 문자만 든 발화"를 "라틴 문자가 하나라도 든 발화"로 고친다. 코드와 0단계 보고(라틴 200건)가 이미 이 규칙이었고, 어휘가 한글 음절뿐이라는 의도에 맞다
5. **어휘 생성 순서**: 어휘는 CTC 길이 제외까지 모든 학습 제외를 적용한 뒤의 학습 전사로 만든다(스크립트 순서 변경). 현재 매니페스트는 CTC 제외가 0건이라 결과가 같다(최종 `train.jsonl`에서 다시 만든 어휘 == `manifests/vocab.json` 확인)
6. **평가 세트 고정**: 정규화 뒤 빈 전사나 오디오 결손이 평가 세트(dev_mix, dev_H, 봉인 test)에서 나오면 전처리를 중단한다(조용히 축소하지 않음). 현재 매니페스트는 평가 세트 누락 0건(`reports/stage0/data_summary.json`의 `dropped_empty_text`, `dropped_missing_audio_eval` 비어 있음)
7. **`<unk>` 평가 표기**: 디코딩 결과의 `<unk>`는 U+318D(ㆍ, 한글 자모 아래아)로 바꾼다. CER_ns의 점수 정규화가 이 글자를 남기고, CER_ws의 학습 정규화도 가설 쪽에서는 이 글자를 남기도록 하여 두 지표 모두에서 `<unk>` 하나가 오류 1자로 센다(이전 구현은 "unk" 세 글자로 풀려 라틴 정답과 맞을 수 있었음). 정답에는 이 글자가 나올 수 없다
8. **평가 정밀도**: full·simulated·real streaming 디코딩과 dev 손실은 모두 학습과 같은 autocast fp16(GPU)으로 계산하고 결과에 `precision`을 적는다(`--fp32` 학습 모델은 fp32). H6.1의 차이가 캐시 때문인지 정밀도 때문인지 가리기 위함
9. **스트리밍 패킷 규약**: 첫 패킷 5,360 샘플(5,120 + 240), 이후 5,120 샘플. 그래야 패킷마다 mel 32프레임 = 인코더 청크 1개가 나온다(아니면 첫 청크가 두 번째 패킷까지 기다려 320 ms가 더 늦음). 6단계 지연 측정과 브라우저 클라이언트도 이 규약
10. **재개 규칙**: 체크포인트는 완료 epoch만 재개할 수 있고(난수 상태·발산 카운터·dev 손실 이력 포함), 중간에 멈춘 `last.pt`와 발산 판정을 받은 런은 재개를 거부한다. 같은 `--run` 디렉터리에 로그가 이미 있으면 `--resume` 없이는 시작하지 않는다(이전 시도의 로그가 섞이지 않게)
11. **fp16 스트리밍 게이트의 추가 보고**: 0단계 게이트(fp16 log-prob 최대 절대차 ≤ 1e-2)는 무작위 초기화 모델에서 쟀다. 학습된 모델은 희박 클래스의 log-prob 절댓값이 커서 fp16 반올림만으로 1e-2를 넘을 수 있으므로(검토 지적), 2단계 끝에 같은 비교를 다시 재고 log-prob 차이와 함께 **확률 최대 절대차와 프레임 argmax 일치율**을 보고한다. H6.1(CER 차이 ≤ 0.1)이 판정 기준이고 log-prob 게이트는 캐시 버그 탐지용이다
13. **1단계 3차 시도 전 처방(2026-10-11 07:02 커밋 b6e27a0, 2차 결과·진단 뒤, 3차 측정 시작 07:23 전)**. 진단(`reports/stage1/diag-2026-10-11.md`) 결론: (가) 처음부터 SpecAugment를 걸면 이 설정(QK-norm 유무 모두, 시드 1, LR 1e-3·2e-3)에서 CTC 정렬이 적어도 5 epoch 동안 시작되지 않았고, SpecAugment를 끄면 속도 교란·동적 청크를 켠 채로도 epoch 2에 시작했다(P1·P5: dev 손실 96, CER 0.57). 즉 SpecAugment를 끄는 것이 충분했고 속도 교란·동적 청크는 방해 요인이 아니었다. 자기조건 피드백·낮은 LR 대안(5e-4·warmup 8,000)은 따로 시험하지 않았으므로 배제한 것이 아니라 더 직접적인 처방을 택한 것이다. 직접 비교: 파일럿 B(QK-norm, 1e-3, 시드 1, 같은 스케줄, SpecAugment 처음부터)는 dev 손실 192→186→190→189였고 3차 시도의 같은 조건(SpecAugment epoch 3부터)은 171→93→82→79→75다. (나) LR 7e-4 이상에서 어텐션 로짓 표준편차가 60~111까지 커지는 현상이 정체와 함께 관측됐고(인과 방향은 확정하지 않음), QK-norm이 이를 1~3으로 억제했다(파일럿 B; LayerNorm의 affine 파라미터가 커지면 경계는 보장되지 않으므로 2단계 보고에 affine 크기·로짓 표준편차를 기록). 변경:
    - **SpecAugment 커리큘럼**: epoch 0~2(2,091 step ≈ warmup)에는 SpecAugment를 끄고 epoch 3부터 켠다(`--augment-start-epoch`, 기본값 3). 속도 교란·동적 청크·dropout은 처음부터. 켜는 시점이 학습을 무너뜨리지 않는지는 P6(6 epoch)로 확인하고 결과를 진단 기록에 적는다
    - **QK-norm 추가(기본값 켬, `--no-qk-norm`으로 끔)**: 어텐션의 q·k에 헤드별 LayerNorm(RoPE 앞). 프레임 단위 연산이라 스트리밍 정확성·미래 불변은 그대로(테스트 추가). `docs/survey/README.md` 결정표에 추가 표기. 이후 모든 단계의 모델은 QK-norm 포함
    - **1단계 스케줄**: 런의 LR 스케줄 총 길이를 2단계와 같은 69,700 step으로 두고 5 epoch만 돈다(`--schedule-steps 69700`). 그래야 warmup 뒤 peak LR이 유지되는 구간(epoch 3~5, SpecAugment 켠 상태)에서 fp16 안정성을 본다. 2단계도 같은 스케줄이므로 1단계 런은 2단계의 앞부분과 같다
    - **dev 손실 판정(규칙 변경 3)**은 그대로 "epoch 3 끝 < epoch 1 끝"이다. 커리큘럼 아래에서는 정렬이 epoch 2에 시작되므로 이 비교가 "학습이 안 되는 런"을 가려낸다
    - 후보는 등록대로 peak LR {1e-3, 2e-3} × 시드 {1, 2, 3}, warmup 2,000. 등록된 대안(5e-4·warmup 8,000)은 원인이 LR이 아니었으므로 쓰지 않는다. 2차 시도의 6런은 "처방 전 설정"으로 발산 표에 남기고 H1 판정에는 넣지 않는다
14. **서비스 경로 정밀도·버퍼**(처음 등록 때 12번, 커밋 b6e27a0에서 번호만 바뀜): 서비스 세션도 평가와 같은 autocast fp16으로 돌리고 `/info`에 precision을 적는다. 끝점에서는 인식 상태(greedy·끝점 카운터·캐시)만 초기화하고 버퍼의 mel 프레임과 fbank 캐리는 버리지 않는다(검토에서 세그먼트마다 300 ms 음성 손실과 320 ms 추가 지연이 생기는 결함 발견). 서버는 flush 뒤 청크당 계산 시간 p50/p90을 보내고 6단계 H6.2는 이 값으로 잰다
15. **재개·sweep 보호와 커리큘럼의 step 정의(Codex 1단계 검토 반영, 2단계 측정 중 코드 변경·Run A 처방 불변)**: 체크포인트에 처방 인자(RECIPE_KEYS)와 dev 손실 규칙 적용 여부를 저장하고, `--resume`는 저장된 처방과 같아야 한다(다르면 `--allow-recipe-change`를 명시하고 `meta-resume-*.json`에 차이를 기록; 원래 `meta.json`은 덮지 않음). `--resume`는 완료 epoch 체크포인트가 없으면 실패하고 `--init`과 함께 쓸 수 없다. dev 손실 비교는 두 값이 모두 유한해야 "내려감"으로 인정한다. SpecAugment 커리큘럼은 **step 시도 2,091**(= 300 s 배치의 3 epoch)로 정의하며, 배치 규칙이 다른 arm(3단계 (d) CR-CTC)은 `--augment-start-step 2091`로 같은 step에 켠다. sweep은 후보 정의 인자의 중복 전달을 거부하고, 런별 `meta.json`과 후보를 대조하며, 3시드·5 epoch 완료·발산 0인 LR만 "채택 가능"으로 표시한다. 1단계 3차 결과의 `min scale`·최대 기울기 노름은 100 step 간격 로그 표본의 값이다(발산 판정 자체는 매 step)
16. **4단계 이어 학습 처방(측정 전)**: `--init`로 시작하는 런은 가중치만 이어받고 옵티마이저·스케줄은 새로 시작한다. 이미 정렬된 모델이므로 SpecAugment와 속도 교란을 처음부터 켠다(`--augment-start-epoch 0 --perturb-start-epoch 0`), warmup 500 step, 스케줄은 15 epoch cosine(`--schedule-steps` = 15 × steps/epoch), peak LR은 2단계 채택 LR의 절반(1e-3), dev 손실 발산 규칙은 적용하지 않는다(처음부터 학습하는 런 전용). 세 후보(통제·TrimTail·Peak-First) 모두 같은 설정
17. **3단계 구체 설정(2026-10-11 밤, 2단계 측정 중·3단계 측정 전)**: 모든 후보는 Run A와 같은 peak LR 2e-3, 시드 1, warmup 2,000, QK-norm, SpecAugment 커리큘럼(step 2,091부터), 동적 청크, 속도 교란, 메모리 설정(상한 0.8, GC 0.8)을 쓰고 `scripts/stage3.py`로 순서대로 돌린다. 평가는 상위 10개 평균의 dev_mix·dev_H full greedy CER_ns(한글 전용)와 Run A 평균 모델과의 짝지은 부트스트랩 구간(`scripts/compare_runs.py`), 참고로 simulated 320·640 ms와 학습셋 1,000발화 CER. (a) `--sc-layers 6 --sc-weight 0.3 --no-sc-feedback`, 100 epoch. (b) `--block ebranchformer --ffn-dim 768 --cgmlp-units 896`(cgMLP·병합 depthwise conv 커널 31, 둘 다 Conformer conv와 같은 BACON 분할), 21.32M = Run A 20.79M의 +2.5 %, 100 epoch.
