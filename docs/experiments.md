# 측정 규칙과 결과

규칙은 재기 전에 적고 커밋한다. 결과는 각 단계 절의 "결과" 소절에만 적고, 규칙을 바꾸면 "규칙 변경" 절에 이유와 시점을 남긴다. 봉인 test는 7단계에서만, 사전 등록한 구성으로 각 1회 잰다.

## 공통 (2026-10-11 규칙, 측정 전)

### 지표
- **주지표 CER_ns**: 공백 제외 음절 CER. 정규화는 whisper-ko-ft와 같다: 소문자화, 글자·숫자·공백·작은따옴표가 아닌 문자는 공백으로, 한국어는 작은따옴표와 공백을 모두 없앤 뒤 글자 단위 편집 거리. 묶음 전체의 편집 수 합 ÷ 정답 글자 수 합. whisper-ko-ft의 Zeroth test 앵커(turbo 제로샷 4.48 %, turbo+LoRA 1.96 %)가 이 정의다
- **보조 CER_ws**: 공백 포함 음절 CER(공백도 글자로 셈, KsponSpeech 정의)
- 구간: 발화 단위 부트스트랩 1,000회, seed 0, 95 %. 두 구성의 비교는 같은 발화를 다시 뽑는 짝지은 구간
- 모든 수치에 체크포인트(epoch, 평균 개수)와 디코딩 모드(full / simulated chunk / real streaming)와 청크·좌측 문맥을 함께 적는다
- 정답에 아라비아 숫자·라틴 문자가 남는 발화(FLEURS·CV)는 **전체**와 **한글 전용 부분집합** 두 수치를 모두 보고한다. 모델 어휘에 숫자·라틴이 없으므로 전체 수치에서는 그 글자가 오류로 센다

### 텍스트 정규화 (학습 정답·평가 정답 공통, 스크립트 하나)
1. NFC 정규화
2. 한글·라틴 문자·숫자·공백 외 문자(문장부호·기호)는 공백으로
3. 공백 축약, 양끝 제거
4. 숫자가 든 발화는 **학습에서 제외**(한국어 숫자 읽기가 둘이라 자동 변환이 틀리기 쉬움). 평가에서는 위 "두 수치" 규칙
5. 라틴 문자만 든 발화도 학습에서 제외(어휘는 한글 음절만). 제외 수는 세트별로 보고

### 어휘
- blank(0), `<unk>`(1), 공백(2), 그다음 학습 전사(정규화·제외 뒤)에 1회 이상 등장한 한글 음절 전부(빈도순). 평가 세트별 OOV 음절 수를 CER 하한으로 보고

### 데이터 분할 (SHA-256, seed 없음)
- Zeroth 고유 문장 3,003개를 `sha256("zeroth-holdout:" + 문장)`의 앞 8자리 16진수를 정수로 보아 `% 100`이 `< 10`이면 **홀드아웃 H**(약 300문장, 그 문장의 발화 전부 ≈ 2,200발화 ≈ 5 h). H 안에서 `% 100`이 `< 5`면 **dev_H**, 아니면 **test_H**(봉인)
- 학습 = Zeroth train − H + FLEURS train(제외 규칙 뒤) + CV22 validated − CV22 dev − CV22 test(path 기준)
- **dev_mix**(1차 선택 지표) = FLEURS validation(한글 전용) + CV22 dev(한글 전용). 두 세트의 편집 수·글자 수를 합쳐 하나의 CER로 계산
- **dev_H**(2차 가드) = Zeroth 홀드아웃 dev
- **봉인 test**(7단계 1회) = Zeroth 공식 test 457(본 문장·못 본 화자, 표시 붙임), Zeroth test_H(못 본 문장·본 화자), FLEURS test 382, CV22 test 472
- Common Voice `other`(미검증)와 `invalidated`는 쓰지 않는다
- 길이 20 s 초과 발화는 학습에서 제외. 25 fps 출력에서 `T' < U + (연속 같은 토큰 수) + 1`인 발화도 제외(CTC 손실 무한대 방지). 모두 수를 보고

### 선택 규칙 (모든 단계 공통)
- 후보 사이 비교는 dev_mix의 CER_ns로 하고, dev_H가 절대 0.3 넘게 나빠지는 후보는 채택하지 않는다
- 채택 임계는 **max(0.3 절대, 2s)**. s = 1단계에서 같은 설정 3시드의 dev_mix CER_ns 표준편차. 상대 기준을 쓰는 가설은 짝지은 부트스트랩 구간이 0을 제외해야 한다
- 같은 비교 안의 런은 같은 업데이트 step 수·배치 규칙·시드를 쓴다(메모리가 남아도 배치를 키우지 않음)
- 체크포인트는 매 epoch 저장, 평가 모델은 dev_mix 상위 10개 평균

### 예산 규칙
- 0단계에서 잰 epoch 시간 × 100 > 14 h이면 2단계 epoch = floor(14 h ÷ epoch 시간), 하한 60. 적용하면 기록
- 단계마다 GPU 시간을 기록한다. 다른 프로그램이 GPU를 쓰는 동안 잰 속도·지연은 "부하 조건"으로 표시한다

### fp16 규칙
- `torch.autocast(device_type="cuda", dtype=torch.float16)` 명시, 파라미터·옵티마이저 fp32, GradScaler 기본값, `unscale_` 뒤 grad clip 5.0
- CTC와 자기조건 CTC 입력은 `log_softmax(..., dtype=float32)`. 단위 테스트로 고정
- **fp16 발산 판정**: 손실 NaN/Inf 3회 이상, 또는 GradScaler scale < 1.0이 100 step 연속, 또는 3 epoch까지 dev CTC 손실이 내려가지 않음. 발산한 런은 기록하고 LR×0.5로 최대 2회 재시작. 발산 횟수는 최종 보고에 표로 남긴다
- 시작 로그에 `torch.cuda.is_bf16_supported(including_emulation=False)` 값을 남긴다(2080 Ti는 False여야 함)

## 0단계: 데이터·코드·마이크로벤치 (2026-10-11 규칙, 측정 전)

### 할 것
- 정규화 스크립트·어휘·분할 매니페스트를 만들고 `manifests/`에 커밋
- 모델·학습·디코딩 코드와 단위 테스트
  - 미래 누출: 미래 프레임을 난수로 바꿔도 현재 청크까지의 출력이 불변(청크 4/8/16/32, 좌측 64/128)
  - 스트리밍 == 오프라인: 캐시 스트리밍 forward와 전체 발화 + 청크 마스크 forward의 log-prob 최대 차이 fp32 1e-5, fp16 1e-2 이내(fbank 경계 프레임 포함)
  - CTC 입력 dtype == float32
  - 과적합: 발화 20개로 CER 0 수렴
- 마이크로벤치: max-duration {200, 300, 400, 600} s에서 피크 메모리·step 시간·데이터 대기 비율, epoch 시간 추정, SDPA 커널 종류

### 가설
- **H0.1**: 25 fps에서 CTC 길이 제약에 걸리는 학습 발화 ≤ 0.5 %
- **H0.2**: max-duration 300 s 피크 메모리 ≤ 9.5 GB, 학습셋 1 epoch ≤ 8분

### 판정
- 단위 테스트 전부 통과 전에는 학습을 시작하지 않는다
- H0.1 위반 발화는 제외하고 비율을 기록. H0.2 위반이면 예산 규칙 적용
- 데이터 대기 비율 > 20 %면 fbank fp16 사전 계산으로 전환하고 기록

### 0단계 결과 보강 (2026-10-11, 1단계 측정 전)
- **1단계 첫 시도 무효**: LR 1e-3 시드 1·2·3이 모두 100~120 step에서 scale < 1.0 100 step 연속으로 멈췄다. 원인은 fp16 불안정이 아니라 CTC 손실 코드의 버그 둘(패딩 프레임의 초기화되지 않은 CTC 기울기, 전치된 비연속 log-prob 뷰에서 CUDA CTC backward 오류; `docs/ai-verification.md`). 수정 뒤 실패 배치 16시드에서 NaN 0회. 세 런은 발산 횟수 표에 "코드 버그로 무효"로만 적고 H1에 넣지 않는다(`reports/stage1/attempt1-invalid-summary.json`)
- **독립 검토 반영**: Codex 0단계 검토 16건을 모두 반영했다(규칙 변경 1~10, `docs/ai-verification.md`). 테스트는 56개(`test_model` 38, `test_prepare_data` 13, `test_service` 5)
- **fp16 게이트 실측**(RTX 2080 Ti, 실제 크기 12층 d=256 1,288 클래스, 무작위 초기화, 800 mel 프레임): 캐시 스트리밍 vs 오프라인 청크 마스크 log-prob 최대 절대차 fp16 autocast 3.4e-3~4.0e-3(청크 4/64, 8/128, 16/128; 캐시 절단 포함), fp32 ≤ 2.9e-6 → 등록 게이트(fp16 1e-2, fp32 1e-5) 충족. fp16에서 청크 경계 뒤 음성을 바꿔도 경계 앞 출력은 비트 단위로 같다(BACON 우측 탭을 가린 뒤 더하는 구현)
- 학습 루프 연기 실행(12 step): 시작 scale 65,536이 256까지 내려오는 동안 8 step 스킵, 이후 업데이트. 이 초기 스킵은 GradScaler의 정상 동작이라 발산 규칙(scale < 1.0)과 무관하다

## 1단계: fp16 안정성·peak LR (2026-10-11 규칙, 측정 전)

- 후보: peak LR {1e-3, 2e-3} × 시드 {1, 2, 3}, warmup 2,000 step(규칙 변경 1; 원래 4,000), 최종 구성 그대로 5 epoch
- 측정: 런별 발산 여부(위 정의), epoch 5의 dev_mix·dev_H CER_ns(full greedy), GradScaler 스킵 횟수와 scale 이력
- **H1**: 2e-3에서 발산 ≤ 1/3
- 판정: 발산 0/3인 LR 가운데 epoch 5 dev_mix 평균이 낮은 쪽을 채택. 둘 다 발산이 있으면 5e-4·warmup 8,000을 더해 반복. 채택 LR의 3시드 표준편차를 s로 기록

### 1단계 결과 — 2차 시도 (2026-10-11 03:22~05:14, `reports/stage1/attempt2-*`)
- 6런 모두 발산 판정. 5런은 규칙 변경 3의 dev 손실 조건(epoch 3 ≥ epoch 1)으로 epoch 3에서 멈췄고(dev_mix 손실 예: 187.3 → 189.7 → 192.2), 1런(2e-3 시드 3)은 warmup이 끝난 직후 step 2,100 부근에서 기울기 노름 67,244·scale 0.5로 scale < 1.0 100 step 조건에 걸렸다(진짜 fp16 불안정)
- 멈춘 시점의 모델은 모두 CTC 학습 초기의 "사전확률 해"에 있었다: dev_mix full CER 0.93~0.95, 출력은 "이 … 니다"뿐, blank 사후확률 평균 0.69. 학습 손실도 step 300 이후 140~390 사이에서 흔들리며 내려가지 않았다
- 해석(당시): warmup 2,000 step(≈ 2.9 epoch) 동안은 LR이 작아 정렬이 시작되기 전이고, 규칙 변경 3의 "epoch 3 vs epoch 1" 비교 구간(2,091 step)은 마지막 91 step을 빼면 warmup이라 "학습이 안 되는 런"과 "정렬 전 정체 구간"을 구분하지 못했다고 보았다. 진단 뒤 밝혀진 실제 원인은 아래 진단 절(처음부터 건 SpecAugment)이며, 이 해석은 기록으로만 남긴다. 또 1단계 런의 cosine 스케줄 총 길이를 5 epoch로 잡아 peak LR이 유지되는 구간이 거의 없었다(step 2,000에 peak, 2,750에 이미 절반). 조치는 아래 규칙 변경 13(진단 뒤 확정)
- 부수 측정: epoch 시간 261~274 s(첫 epoch는 디스크 캐시 때문에 470~572 s), 0단계 추정 7.8분보다 짧다. 초기 GradScaler 스킵 9~18회(scale 65,536 → 64~128 안착)

### 1단계 진단 (2026-10-11 05:17~06:05, 판정에 쓰지 않는 탐색 실험, `work/diag/`)
- **이어 학습**: 1e-3 시드 1의 epoch 3 체크포인트에서 LR 1e-3(warmup 200, 6 epoch cosine)으로 5 epoch 더 → dev_mix CER 0.935 그대로, dev 손실 183.9, 기울기 노름 1,479 → 4,564 → 37,436으로 커지다 step 3,600에서 scale 붕괴. 정체가 아니라 불안정
- **실제 발화 20개 과적합**(증강·속도 교란 없음, LR 5e-4 고정, dropout 0): step 100에 train CER 0.013, step 150에 0.000, 손실 1e-3까지 → 데이터·특징·모델·CTC 경로는 정상. PCM 저장소도 원본 parquet 음성과 비트 단위로 같음(Zeroth 37발화 표본)
- **함께 관측된 불안정**: 어텐션 로짓(q·k/√d) 표준편차가 epoch 1(LR ≈ 3.5e-4) 2 안팎 → epoch 2(LR 7e-4) 2~8 → epoch 3(LR 1e-3) 13~27 → 이어 학습 중 60~111로 커졌다(블록 1·2·5·7). softmax 포화는 정렬 학습을 막고 기울기를 키울 수 있다(어텐션 로짓 성장 불안정; Dehghani 2023, Wortsman 2023). 다만 QK-norm으로 로짓을 묶은 파일럿 B도 정체했으므로 로짓 성장이 정체의 원인인지 결과인지는 확정하지 않는다. 가중치 노름도 계속 커짐(`subsampling.out` 10 → 48, `out_proj` 24 → 46; weight decay 1e-6은 억제력 없음)

모두 2026-10-11. 1~12와 14는 1단계 2차 시도 전(커밋 d095b8e·3cece48, 03:21), 13은 2차 결과와 진단을 본 뒤 3차 시도 전(커밋 b6e27a0 07:02, 3차 시작 07:23), 15~16은 1단계 판정 뒤 2단계 측정 전(Codex 1단계 검토 반영). 1단계 첫 시도는 코드 버그로 무효 처리(0단계 결과 보강 참조). 독립 검토(Codex, `docs/ai-verification.md`)의 지적을 반영했다.

1. **warmup 4,000 → 2,000 step(모든 단계)**. 1단계 5 epoch = 3,485 step이라 warmup 4,000 안에서 끝나 peak LR에 닿지 않는다(마지막 LR이 peak의 87 %). 2,000 step ≈ 2.9 epoch. 2단계(69,700 step)도 2,000
2. **step 정의**: "같은 업데이트 step 수"를 "같은 optimizer step 시도 횟수"로 읽는다. LR 스케줄·예산·동일 비교는 시도 횟수 기준이고, GradScaler가 건너뛴 횟수(`skipped`)와 실제 업데이트 수(`updates`)를 모든 런에서 함께 기록·보고한다
3. **dev CTC 손실 발산 조건 구체화**: 매 epoch 끝에 dev_mix의 최종 헤드 CTC 손실(full context, 발화 평균, 학습과 같은 정밀도)을 기록하고, **epoch 3 끝 값 ≥ epoch 1 끝 값**이면 발산으로 판정해 런을 멈춘다. 처음부터 학습하는 런에만 적용(`--init`로 이어 학습하는 4단계에는 적용하지 않음)
4. **라틴 제외 문구**: "라틴 문자만 든 발화"를 "라틴 문자가 하나라도 든 발화"로 고친다. 코드와 0단계 보고(라틴 200건)가 이미 이 규칙이었고, 어휘가 한글 음절뿐이라는 의도에 맞다
